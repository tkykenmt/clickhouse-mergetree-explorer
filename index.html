このツールについて

ClickHouse がデータをどう置き、どう読むのかを、さわって確かめる教材です。社内外のトレーニングとデモに使います。単一の HTML ファイルで、ブラウザで開くだけで動きます。

  • 学習レベル: Lv1〜8 で要素が段階的に解禁。経験者は「ぜんぶ表示」で即 Lv8。URL に #lv=4 を付けると開始レベルを指定できます(研修用)。前回のレベルと文字サイズは記憶されます。
  • デプロイ形態スイッチ(Lv8): ☁️ Cloud(SharedMergeTree)⇄ 🖥 セルフホスト(Replicated)。SQL・図・挙動が丸ごと切り替わります。
  • 題材は全画面共通: SaaS のアクセスログ events テーブルと1本の共通クエリ。どの画面も同じデータの話をしています。
黄 = ClickHouse / 主役・強調 緑 = granule / データ シアン = インデックス / ポインタ / S3 橙 = Skip Index / 警告 赤 = 破壊的・偽陽性

数値・仕様は ClickHouse 公式ドキュメントに準拠(最終確認 2026-07-23)。一次情報は 📚 ドキュメントマップから。シミュレーションの Part 名・行数は説明用の縮尺模型です。

読み方: 同じデータ範囲を3通りに区切った図です。処理 Block は granule の整数個から組み立てられるので境界は granule と一致します(緑と黄の線が揃う)。一方圧縮ブロックはバイト量基準なので granule 境界とズレます(青の線)。だから Mark には「圧縮ブロックの位置」と「展開後のずれ」の2つのオフセットが必要になるわけです。Granule はディスクにもメモリにも実体がない「索引が指すための目盛り」、処理 Block はファイルとして存在しない「実行時だけの入れ物」です。

この対応関係も変更なし。圧縮ブロックが S3 上のオブジェクト内に並ぶだけで、Mark の2段オフセットも処理 Block の組み立ても同じです。

Skip Index(primary.idx 以外の絞り込み索引)

キーに載っていない列の絞り込みを担うのが skip index。仕組みは2系統あります。
text index(転置索引・26.2 GA)
辞書+ポスティングリストで token → granule を直接特定。索引起因の偽陽性なし。url のような文字列検索の推奨で、このテーブルの skp_idx_url_text もこれ(動きは「クエリと読み取り」STAGE 4 で)。▸ ファイル構造を見る
要約型(minmax / set / bloom_filter)
granule を GRANULARITY 個まとめた単位(index granule)ごとの要約で、値を「含みえない」と証明できた granule 群を読み飛ばします。偽陽性はあり、行の位置も分かりません。数値範囲や ID 向き(全文検索用途では非推奨化)。このテーブルの ts_minmax がこれで、動きは「クエリと読み取り」の「ts 7/20 以降」条件で試せます。▸ ファイル構造を見る
要約型の3方式 — 違いは「要約に何を控えるか」だけです。
minmax
要約 = 区間の最小値と最大値。範囲・大小条件(<、BETWEEN)に強く、要約が2値だけなので索引は最小。挿入順と相関する列(時刻・連番)で真価を発揮します。
set(N)
要約 = 区間に現れた値の集合(最大 N 個。あふれると「何でも含むかも」に退化して効かなくなる)。カーディナリティの低い列の等価・IN 向き。
bloom_filter
要約 = ハッシュを立てたビットマップ。値の種類が多い列の等価・IN 向きで、偽陽性率を指定できます。文字列向け派生の tokenbf / ngrambf は全文検索では text index に交代。
実験室(要約型の原理): 下の8つの Granule の実データ(events.url を数値トークンに単純化)から index granule(要約)が計算されます。TYPE を切り替えると要約の中身が変わります。

Projection の定義(設定はデッキと連動)

動作は変更なし。Projection は Part の中身の一部なので、S3 上の Part オブジェクトに一緒に格納され、マージも親 Part と一体で行われます。
⚠ 代償と制約: INSERT のたびに Projection の分も書く(挿入負荷+ストレージ増)。まず本体の ORDER BY 設計を済ませ、実測で遅いクエリにだけ足すのが定石です。SET force_optimize_projection = 1 にすると「使われなければエラー」になり検証できます。FINAL とは併用不可、軽量削除(DELETE FROM)ともデフォルト非互換(v24.7+ の lightweight_mutation_projection_mode で緩和可)。GROUP BY を含む Projection は AggregatingMergeTree として Part 内に格納され、事前集計にも使えます。

🔬 深掘り: ORDER BY vs PRIMARY KEY(並びと索引の分離)
💡 ORDER BY = ディスク上の並び順を決める。PRIMARY KEY = そのうちprimary.idx に載せる接頭辞を決める。スライダーで PRIMARY KEY を短くして、左(並び)は不変・右(索引)だけ痩せることを確認してください。

DDL を組み立てる

PRIMARY KEY の長さ 3列
  • 省略時は PRIMARY KEY = ORDER BY。多くのテーブルはこの状態で運用されています。
  • 別指定する場合、PRIMARY KEY は ORDER BY の接頭辞でなければなりません(例: ORDER BY (a,b,c) に対し (a) や (a,b) は OK、(b) や (a,c) は NG)。
  • RDBMS と違い一意制約ではありません。同じキーの行が何行あっても OK。
  • 短くする動機は primary.idx のメモリ削減。SummingMergeTree 等で ORDER BY に集計ディメンションを全部並べる必要があるが、検索は先頭の数列でしかしない、という時に効きます。
このタブの内容は変更なし。ORDER BY / PRIMARY KEY の意味論、primary.idx の構造とメモリ常駐はローカルでも Cloud でも同一です。なお Cloud では ENGINE = MergeTree と書くだけで自動的に SharedMergeTree にマッピングされます。

STAGE 6: 処理 Block に束ねて並列実行

並列実行(granule → Block → スレッド)

枝刈りを生き残った granule のその後

生き残った granule は max_threads 本のスレッドに分配され、複数 granule を束ねた処理 Block(既定 ≤65,409 行)単位でベクトル化(SIMD)実行されます。つまりこのタブの最適化はすべて「Block に載せる行を減らす」工夫です。Granule・圧縮ブロック・処理 Block の境界対応は、「構造と書き込み」タブで Part を開き、.bin か .cmrk2 のバイト図の中のリンクから図解が開きます。

Query cache / Query condition cache

2種類の「読まずに答える」キャッシュ
use_query_cache
クエリの結果そのものをキャッシュ。同一クエリの再実行(ダッシュボードの自動更新など)で granule を1つも読まずに返せます。明示的にオプトイン。
use_query_condition_cache
WHERE 述語ごとに「どの granule が条件を満たしたか」を記憶。次回は一致 granule だけ読みます。結果でなく枝刈りの答えをキャッシュするので、似たクエリにも効きます。
