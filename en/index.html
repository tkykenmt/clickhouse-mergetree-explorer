How to read: The same data range, divided up three different ways.A processing Block is assembled from a whole number of granules, so the boundaries coincide with granules (the green and yellow lines align). By contrast, compressed blocks are cut by byte sizeso they drift from granule boundaries (blue lines). That is why a Mark needs two offsets: the compressed block position and the shift after decompression. A granule has no physical form on disk or in memory — it is a ruler mark for the index to point at — while a processing Block is a runtime-only container that never exists as a file.

This mapping also No change. Compressed blocks simply line up inside an object on S3 — the two-level Mark offsets and the processing-Block assembly stay the same.

Skip Index (narrowing indexes other than primary.idx)

Narrowing down on columns not in the key is the job of skip indexes. There are two families of mechanism.
text index (inverted index, GA in 26.2)
A dictionary plus posting lists pinpoint token → granule directly. No index-induced false positives. The recommendation for string search such as url — this table has skp_idx_url_text of this kind (see STAGE 4 under Query & Reads).▸ View the file structure
Summary-type (minmax / set / bloom_filter)
A summary per unit of GRANULARITY granules (an index granule); it can prove a value “cannot contain” can be proven — those granule groups are skipped. False positives exist, and row positions are unknown. Suited to numeric ranges and IDs (deprecated for full-text search). This table has ts_minmax of this kind; watch it work with the ts on/after 7/20 condition under Query & Reads.▸ View the file structure
The 3 summary-type methods — the only difference is what each summary records.
minmax
Summary = per-range Min and max values. Strong for range and comparison conditions (<, BETWEEN), and since the summary is just two values the index stays minimal. It shines on columns correlated with insert order (timestamps, sequence numbers).
set(N)
Summary = what appeared in the intervalSet of values(up to N entries. On overflow it degrades to “might contain anything” and stops helping). Best for equality and IN on low-cardinality columns.
bloom_filter
Summary = hash bits set in a bitmap. Suited to equality and IN on high-cardinality columns, with a configurable false-positive rate. For full-text search, the string-oriented variants tokenbf / ngrambf give way to the text index.
lab (how summary-type indexes work): the index granules (summaries) are computed from the actual data of the 8 Granules below (events.url simplified to numeric tokens). Switching TYPE changes what the summary holds.

🔬 Deep dive: the Projection lab and when to use it versus MVs

Projection definition (the setting is linked to the action deck)

The behavior is No change. A projection is part of the Part’s contents, so it is stored inside the Part object on S3 and merges together with its parent Part.
⚠ Costs and constraints: every INSERT also writes the projection (more insert load + more storage). The standard play is to finish the base ORDER BY design first, then add projections only for queries measured to be slow.SET force_optimize_projection = 1 makes it an error when the projection is not used, which lets you verify it fires. It cannot be combined with FINAL, and is by default incompatible with lightweight DELETE (DELETE FROM) as well (v24.7+ resolves this via lightweight_mutation_projection_mode can relax this). Projections containing GROUP BY are stored inside the Part as AggregatingMergeTree and can also serve pre-aggregation.

💡 ORDER BY = on-disk Sort order is decided here.PRIMARY KEY = of which The prefix that goes into primary.idx is decided. Use the slider to shorten the PRIMARY KEY, then Left (the ordering) stays immutable — only the right (the index) slims down — confirm this.

Build the DDL

PRIMARY KEY length 3 columns
  • If omitted, PRIMARY KEY = ORDER BY.Plenty of tables run in exactly this state.
  • When specified separately, PRIMARY KEY must be Prefix of ORDER BY is required (e.g. against ORDER BY (a,b,c), (a) and (a,b) are OK, while (b) and (a,c) are not).
  • Unlike an RDBMSNot a uniqueness constraint. Any number of rows may share the same key.
  • The motivation for keeping it short is Reducing primary.idx memory. Effective when SummingMergeTree and friends force every aggregation dimension into ORDER BY, yet searches only ever use the first few columns.
The content of this tab No change. The semantics of ORDER BY / PRIMARY KEY and the structure and memory residency of primary.idx are identical locally and in Cloud. Note that in Cloud, ENGINE = MergeTree is all you write — it maps to SharedMergeTree automatically.

Parallel execution (granule → Block → thread)

What happens next to the granules that survived pruning

Surviving granules: max_threads threads share the reads, proceeding in units that bundle multiple granules — Processing Block (default ≤65,409 rows)units, with vectorized (SIMD) execution. Every optimization on this tab therefore boils down to reducing the rows that land on a Block. For the boundary mapping between granules, compressed blocks, and processing Blocks, open a Part on the Structure & Writes tab — the links inside the .bin or .cmrk2 byte diagram open the boundary diagram.

Query cache / Query condition cache

Two kinds of “answer without reading” caches
use_query_cache
the query’s The result itself is cached. Re-running the identical query (dashboard auto-refresh and the like) can answer without reading a single granule. Explicitly opt-in.
use_query_condition_cache
For each WHERE predicate: “Which granules matched the condition” is remembered. Next time only matching granules are read. It caches the pruning answer, not the result, so similar queries benefit too.
